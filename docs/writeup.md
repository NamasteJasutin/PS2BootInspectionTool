# What a PlayStation 2 does between power-on and the game

Every PlayStation 2 owner has seen it thousands of times: a few seconds of black, then a dark field of translucent towers drifting past the camera, a soft chord, a short dive into blur, and either the clock screen or the "PlayStation 2" logo and the game. It lasts a few seconds and almost nobody has looked at it closely.

There is one reason to. The towers are not decoration. They are a picture of the console's play history, read from the memory card at boot: every title ever launched owns six places in a grid, the first launch plants a tower, and more appear as the launch count rises. Two consoles never show the same boot screen, and a console booted without its memory card shows an empty field.

This article walks the sequence from the reset vector to the first instruction of a game: how the BIOS is packed, what the two processors do during the black period, how the history file becomes geometry, what each render stage contributes, how the chime is synthesised rather than played back, what the red warning screen is, and how the hand-over to a disc works, including the detail that the logo lettering is read from the disc, not the BIOS.

Everything here comes from a static reading of one BIOS, ROM 2.00 E of an SCPH-70004 slim console (built 14 June 2004), with cross-checks against a few other builds. No hardware capture and no emulator trace was used. Code paths, data layouts, constants and formulas were read from the decompiled program and can be checked; durations, hardware behaviour and the names of SDK calls were inferred and are marked as such where it matters. The companion repository, linked at the end, holds a tool that replays the sequence from the reader's own BIOS, memory card and disc image, plus the full notes with addresses for every claim.

## The ROM: a flat archive and a small LZ format

A PS2 BIOS image is 4 MB and is not a file system. It is a flat concatenation of modules described by a table called ROMDIR. Each entry is 16 bytes: a ten-byte name, a 16-bit size of an "extended info" record, and a 32-bit module size. Modules lie back to back in table order, each padded to 16 bytes, so an offset is the sum of the padded sizes before it. The table is found by searching for its first entry, always named RESET.

The modules that matter for booting: RESET, the code at the reset vector; KERNEL, the EE kernel (about 94 KB); EELOAD, a small loader the kernel runs as its first thread; IOPBOOT and IOPBTCONF, the IOP's boot program and module list; OSDSYS, the on-screen display program that draws the towers and menus; OSDCNF and EELOADCNF, nested archives with alternative IOP module lists; PS2LOGO, the logo program; OSDSND, the IOP sound driver; and five archives holding fonts, sound banks, textures and icons. ROMVER is a 14-character string: for the subject console, version 2.00, region E, console type C (retail), date 20040614.

OSDSYS and PS2LOGO are not stored as plain executables. Each is a tiny ELF with one loadable segment whose entry point is a decompression stub; the real program is an LZ-compressed stream inside the segment. OSDSYS's stream is 363 KB and unpacks to 823 KB at 0x200000, after which the stub jumps to 0x200008; a global context structure that most of the program uses sits just below, at 0x1F0000. PS2LOGO's stream unpacks to about 200 KB at 0x100000. The same scheme compresses the kanji font and most asset-archive entries.

The format, derived from the stub's decoder, is simple. The stream begins with a little-endian 32-bit decompressed size. Then come groups, each introduced by a big-endian 32-bit descriptor. Its top 30 bits are flags for the next 30 tokens, most significant first; its low two bits are a value *n* from 0 to 3 choosing how this group's 16-bit match words split between offset and length. A token with flag 0 is one literal byte. A token with flag 1 is a big-endian 16-bit word *h*: the match offset is `(h & (0x3FFF >> n)) + 1` bytes back from the end of output and the length is `(h >> (14 − n)) + 3`. With *n* = 0 a group reaches 16 KB back but copies only 3 to 6 bytes; with *n* = 3 it reaches 2 KB back and copies 3 to 34. Overlapping copies work as in LZ77. There is no checksum and no end marker beyond the size.

## Power-on: two processors and three IOP boots

Both CPUs start at 0xBFC00000, the top of the ROM. The first instructions read the processor ID register: a value below 0x59 is the R3000-class IOP, which jumps to 0xBFC02000; anything else is the Emotion Engine, which jumps to 0xBFC00800. From here the two run in parallel and meet only through a flag word in the SIF, the bus between them.

The IOP's reset code looks up IOPBOOT in the ROMDIR. IOPBOOT reads IOPBTCONF and loads 29 modules in order: the kernel pieces (memory, loader, exceptions, interrupts, DMA, timers, threads), then the I/O manager, module loader, ROM driver, SIF manager, LOADFILE, CDVDMAN, FILEIO, SECRMAN and a module called EESYNC. SIFMAN sets bit 0x10000 of the SIF flag word. EESYNC is 0x160 bytes of code whose only job is to register a post-boot callback that sets bit 0x40000 once every module has started: "the IOP is ready".

The EE's reset code calls the RDRAM module (also in ROM) to train memory, copies KERNEL to 0x80000000, and jumps to it. The kernel initialises the TLB, interrupt and DMA tables, GS, timers and FPU, clears user memory, starts its DECI2 debugging manager (idle without a host), and spins until the IOP's SIFMAN bit appears. Then it copies EELOAD to 0x82000 and starts it as a thread with no arguments.

That absence of arguments is what distinguishes a cold boot. Every later `LoadExecPS2`, and a game's `Exit()`, goes through the same kernel routine, which terminates all threads, resets the hardware, re-copies EELOAD and starts it with an argument block naming a program. EELOAD with no arguments waits for the IOP's ready bit, sets up RPC, and loads `rom0:OSDSYS` through the IOP's LOADFILE service to 0x100000.

OSDSYS's first act is to reboot the IOP. It sends a reset carrying the string `rom0:UDNL rom0:OSDCNF`, which makes the IOP's update loader boot the list inside OSDCNF: 39 modules, including the extended CD/DVD driver, the memory-card manager and server, the pad, multitap and remote drivers, a module that silences the sound chip, and OSDSND. The EE spins until the ready bit returns. A third IOP boot happens when a game is launched.

What follows in OSDSYS's main function, in order, is the content of the black period. It binds the CD/DVD and memory-card libraries. It looks on both cards for a system-update executable, which is the first card access and where the card is mounted. It initialises the pad libraries. It loads the asset archives: about 1.7 MB read through the IOP's file service, 1.1 MB of it LZ-decoded on the EE, including the 738 KB kanji font. It uploads 410 KB of samples to the sound chip. It reads ROMVER and performs a certification handshake with the drive controller, passing version, region and console type. It reads the NVRAM configuration block carrying language, screen setting, time zone and a bit that says whether first-time setup has been done. It loads the play history from the card. It registers its three UI modules (opening, clock/menu, browser) as sleeping threads, starts a thread that polls the drive's disc-type register once per field, initialises video (640×256 interlaced for PAL, 640×224 for NTSC), installs a VBlank handler, and wakes the opening thread.

None of these durations was measured. Estimates from data sizes and typical bus speeds put the two IOP boots at 0.8 to 2.0 seconds together, the asset load at 0.4 to 1.0, the sound upload at 0.15 to 0.4, the card mount at 0.1 to 0.5, and everything else under a tenth of a second. The sum is roughly 2.0 to 4.5 seconds of black before the first tower frame, consistent with the commonly reported "about three seconds" on a slim console but unchecked against a capture. Neither the disc nor the sound gates the first frame: the opening consults the disc thread only to decide when the dive may begin, and the chime is a queued command sent at the next VBlank.

The opening thread, once woken, queues the chime, uploads about 300 KB of textures, builds the tower geometry from the history table, uploads a VU1 micro-program, and waits for a VBlank. Its frame loop forces the first one or two frames black, so the towers appear within three VBlanks of initialisation finishing. The chord is keyed one to three fields before the first visible frame; its main chord enters two thirds of a second later.

## The towers are your play history

The file is `B?DATA-SYSTEM/history` on the memory card, where `?` is a region letter patched in at boot from ROMVER: I for Japan, A for America, E for Europe, C for China. On the subject console that is `mc0:/BEDATA-SYSTEM/history`.

The file is 462 bytes: 21 records of 22 bytes, a raw image of a table in memory, with no header, version or checksum. Each record is:

- 16 bytes: the title ID, NUL-padded. For a PS2 disc, the 11-character ID decoded from the disc (four letters, underscore, three digits, dot, two digits); for a PlayStation disc, the file name from the `BOOT` line of its SYSTEM.CNF; every DVD-Video shares one record under a fixed name. A zero first byte marks an empty slot.
- 1 byte: launch counter, starting at 1.
- 1 byte: a six-bit mask of the towers this title has earned, starting at 0x01.
- 1 byte: the index (0 to 5) of the bit most recently added, or 7 once the record is maxed out.
- 1 byte the code never writes.
- 2 bytes: a little-endian date, `day + (month << 5) + ((year − 2000) << 9)`, of the most recent launch. No time of day, no per-launch log.

At boot the table is read from port 0, then port 1, and zeroed if both fail. That table is what the opening draws: no card, or no file, means no towers. This is why PCSX2 users rarely see them: fast boot skips the OSD entirely, so the file is never created, and a card full of saves still gives an empty field until a title has been launched through the full boot.

The update happens at launch, after the disc has been accepted and just before control leaves OSDSYS. The code reloads the table and walks all 21 records once, tracking an eviction candidate (lowest count, ties broken by earlier date, with a quirk: the date minimum is not reset when a lower count turns up later in the scan) and looking for a record matching the first 16 bytes of the title. If one matches, its date becomes today and its count rises by one; at 14, 24, 34, 44 and 54 a random bit not yet in the mask is added and becomes the record's growing bit. After 54 launches all six bits are set; the counter continues to 63, and on the 64th launch the record freezes at count 63, index 7.

If no record matches, the title is new. An empty slot is chosen at random, not the first. If there are none, the eviction candidate is overwritten and its 22 bytes appended to `history.old`. The random numbers come from the C library generator, never seeded at boot but stirred before each choice by calling it `minute × 60 + second` times from the clock, so the same history yields different tables on different consoles. Audio CDs and failed launches are never recorded. The save fails silently.

Now the geometry. There are 14 × 9 = 126 positions, and a fixed table gives each of the 21 records six of them, so no two records share one (21 × 6 = 126). The assignment is irregular, so a title's towers are near each other but interleaved with neighbours. For each record and each of its places *k*: if *k* is the record's index, the place holds the growing tower; otherwise, if bit *k* of the mask is set, a finished tower; otherwise nothing. A finished tower has fill = 1, size = 1. A growing one takes a step *n* = count while count < 14, otherwise `4 + (count − 14) mod 10`, and looks up fill = {0.2, 0.4, 0.6, 0.8, then 1} and size = {0.1 for the first five steps, then 0.2, 0.3, … 1}.

So the life of one title on screen: launches 1 to 4, a short stub fades in from 20 to 80 percent opacity. Launches 5 to 13, it lengthens 10 percent per launch, reaching full length at 13. Launch 14, it becomes permanent and a new stub appears in another of the title's six places. One more every ten launches until all six stand at 54.

A tower is a box 4 units square whose half-length along the camera axis is `max(size × 30, 3)`. Its centre is pushed back by `fill × 30 − half-length`, so the near end of a filled tower sits at the same depth whatever its length, and growth is visible as the far end extending away. Positions come from a 14 × 9 table in model coordinates, mapped to world space as `x = (mx + 4.8) × 4`, `y = (my − 6.5) × 4`, `z = (mz + 4) × 12 + 150`: a grid spanning about −36 to +32 horizontally and −21 to +21 vertically around depth 168, pitch 5.2. Brightness comes from a 20 × 20 light map computed once from two radial falloffs plus a deterministic jitter, clamped to 32 to 220, so towers towards one corner are lit more than the other. One honest gap: whether row 0 is the top or the bottom of the screen was not confirmed against a capture.

## Building the frame

The module writes GS registers directly through a small packet builder. A VU1 micro-program of 229 instructions transforms and lights the towers; everything else is EE code emitting sprites and strips.

**Camera.** A point moving along +Z with second-order kinematics (position, velocity, acceleration, and a jerk term for Z), integrated once per frame with a step of 1.0 on NTSC and 1.2 on PAL, so both take the same wall-clock time. It starts at (0, 0, 16) with roll −0.12 radians, forward velocity 0.04 per frame and roll velocity 0.001 per frame. A stage counter advances when Z crosses 16, 56 and 104. Stage 1 is idle drift with a tiny jerk; it ends when the disc state has settled and more than two seconds have passed, or after ten seconds regardless. Stage 2 is the dive: forward acceleration 0.0099 per frame², roll acceleration 0.000195. Stage 3, Z > 104, ends the scene. Simulating the integrator gives a minimum of about 4.1 seconds (2 of drift, 2.1 of dive).

**Towers.** The frame is cleared to black. Towers are drawn with depth test and write, textured with a 256 × 256 wall texture, sorted far to near by `|Δx| + |Δy|` from the camera. Each is rotated a fixed pseudo-random number of quarter turns derived from its column and row, and growing towers additionally sway ±10 degrees with a 360-frame period, so stubs rock while finished towers stand still. The near end gets the light-map brightness, side faces 0.8 of that, and the far end black, so every tower fades into the dark along its length. The faces go through VU1 as strips, lit by three directional lights at 1.0, 0.8 and 0.8 plus 0.4 ambient. An open question lives here: the near cap faces the first light exactly, giving a lighting factor of 1.4, and with light-map values up to 220 the product exceeds the 8-bit range the GS keeps; the micro-program has no clamp. Whether this wraps on hardware, or the cap normal's sign was misread, is unverified.

**Temporal smear.** The previous frame, saved at half width, is drawn over the fresh towers with a constant blend of 0x50/0x80: 0.625 of the previous frame plus 0.375 of the current. This one blend produces the long trails; the towers themselves are sharp.

**Fog.** Six layers of the 17 × 17 mesh at depths 134 down to 109 in steps of 5, each with one of three 64 × 64 fog textures, additive at about 16 percent with a blue tint, each scrolling at its own rate.

**Orbs.** While the camera is nearer than Z = 73, four coloured lights (green, magenta, red, violet) move on Lissajous paths around depth 88, each a soft disc 1.6 units wide plus a white core, additive, with a four-frame ghost and a 128-entry ring of past positions drawn as an anti-aliased line fading to the tail. The phase seed comes from the unseeded generator, so it is the same after every cold boot.

**Glass cubes.** Five cubes of half-size 1.8, tinted (112, 112, 152), at fixed positions between depths 82 and 111, tumbling at 0.001 to 0.004 radians per frame. Each visible cube takes ten passes. The frame is first copied to an off-screen page, and the back faces are drawn into that copy: an opaque pass sampling the live frame displaced along the face normal (refraction), an alpha-only noise texture writing a blotchy pattern into destination alpha, a reflection pass adding a 128 × 128 reflection map (a photograph of rubble) through that alpha, then a second noise texture and second reflection. The front faces are drawn into the live frame the same way but sampling the copy that now contains the back faces, so light appears to bend through two layers of glass. The alpha-mask reading was not confirmed on hardware, and the tool stands in with two passes.

**Defocus and fade.** Once Z exceeds 56, up to three passes of "copy the frame to about seven eighths size and stretch it back", bilinear, one more pass per 12 units of depth. A black sprite with alpha `(z − 72) × 4` clamped to 128 takes the picture to black between Z = 72 and 104; the same routine forces the first two frames black.

**Lettering and letterbox.** Once Z exceeds 18, a counter runs 0 → 240 → 0 in steps of 4 per frame and the lettering's alpha is the counter clamped to 112: a 28-frame fade-in, 64 frames held, 28 out, two seconds at 60 Hz. The two lines of the 256 × 64 texture sit side by side at y = 105 (NTSC) or 120 (PAL), at half brightness. Two black bars leaving a 16:9 window are drawn unless Screen Size is Full; both 4:3 and 16:9 get them.

On the clock, fastest case: 0.67 s main chord; 0.83 s (Z = 18) lettering in; 2.0 s (Z = 21) dive begins and a sound cue is chosen; 2.4 s lettering out; 3.35 s (Z = 56) defocus; 3.65 s (Z = 72) fade begins, orbs and cubes stop at 73; 4.1 s (Z = 104) scene ends.

## The chime is a score, not a recording

The boot sound is not a sample. It is a sequence in a MIDI-like format, played by the IOP's driver through the SPU2's hardware voices and envelopes from a bank of nine short samples. OSDSND is built from Sony's PlayStation-era SPU and sequence libraries ported to the SPU2; it writes the SPU2 registers itself and exposes its functions over SIF RPC, with an OSD-specific command set on top that understands a bank header tagged `SShd` and a sequence tagged `SSsq`.

At boot OSDSYS uploads the boot bank's samples (about 356 KB) to SPU2 RAM, registers two banks, opens eight sequences (boot, menu transition, clock ambience, two timer cues, logo cue, warning ambience, disc transition), sets each one's volume (66 of 127 for the boot sound), sets reverb preset 4 on both cores, and starts the sequencer timer. The timer is a line counter with compare value 256, so the sequencer runs at about 61.04 Hz on PAL and 61.46 Hz on NTSC, inferred from nominal line rates; the tempo arithmetic assumes 60 Hz, so the sequence plays about 1.7 percent fast on PAL and 2.4 percent on NTSC. The reverb return ramps from zero to about 15 percent over the first 60 queue flushes; until then the sequences are dry.

The bank holds 17 programs, 37 tones, 9 samples. A tone is 16 bytes: note range, root note (plays at 44.1 kHz), fine tune in sixteenths of a semitone, sample offset, two raw SPU ADSR registers, volume, pan and flags, one of which is the reverb send. The boot programs are layered: each note of program 0, the main chord, starts three voices of one pad sample, two detuned by a few sixteenths and panned hard left and right, the third a fourth higher in the centre with reverb. The driver writes volume, pitch, start address and ADSR to the voice; the envelope is the hardware's, with nothing added in software. The sequence is MIDI-like (480 ticks per quarter, 90 bpm) with eight notes, expanding to 17 voices, at most 12 at once. No loops, no bends, one tempo.

What it plays, in nominal seconds. At 0.01 s, three things: a looped tonal cluster about 15 semitones below its root with a 2.7-second linear attack, so it only fades in; a 3.9-second one-shot metallic texture an octave down as a left/right pair; and the same texture 19 semitones down as the low rumble bed. At 0.67 s the main chord enters: the pad as three voices with a 0.12-second attack, the loudest element, the mix peaking between 0.75 and 1.0 seconds; a low drone with a 1.6-second attack enters alongside. At 2.0 s the drone is released, at 3.33 s the chord (exponential release, time constant about 2.7 seconds), at 3.37 s the rumble. At 4.0 s a quiet second swell a fourth below the chord, then quieter entries at 4.67 s and 6.33 s. At 9.17 s the last note is released and the sequence ends with voices still ringing.

Which brings up the three cues. When the dive begins, the opening sends one of three commands. For a PlayStation disc, audio CD or DVD-Video it stops the boot sequence with a release-rate override of 0x0F: every sounding voice's release is rewritten as linear at that rate and keyed off, a fade of at most 1.37 seconds. For a PlayStation 2 disc it starts a four-note transition cue and stops the boot sequence with rate 0x11, at most 5.46 seconds, so the chord hangs under the logo screen. For anything else, including no disc, it starts a 1.25-second four-note cue that leads into the menu and lets the boot sequence ring out.

Nothing was auditioned. Sample descriptions come from spectra of the decoded waveforms, envelope times from the standard SPU rules, and the reverb is identified only by its coefficients; its contribution was not simulated, which is why the tool plays the chime without it.

## The warning scene

OSDSYS keeps a disc-state code refreshed once per field from the drive's disc-type register. Zero (no disc or tray open) becomes code 100. Register values 1 to 4 are "detecting". 0x12 and 0x13 are PlayStation 2 CDs (codes 0x6C, 0x6D), 0x14 a PlayStation 2 DVD (0x6E), 0x10 and 0x11 PlayStation discs, 0xFD an audio CD, 0xFE a DVD-Video, and 0xFF illegal or unrecognised media, code 0x74. Illegal is sticky: it stays until the register reads zero, that is, until the disc is removed. It is also forced from outside when EELOAD's loader rejects a program and when a launch fails verification; the browser and menu, asked to start such a disc, hand over to the warning scene.

Code 0x74 is what selects the red screen. No disc does not lead here: code 100 after the opening leads to the clock and main menu. The warning is for media the drive could not accept, and it stays up until the disc is removed or replaced.

The scene is a slow dolly through additive fog towards a flickering dark-red light, with five small glass prisms in front of it, heavy frame feedback, and the per-language text fading in once the camera stops. The camera starts at depth 672 at 2.16 units per frame, decelerating by 0.0178 per frame², tuned to arrive at depth 800 after about 103 NTSC frames with almost no velocity left; the timeline then freezes everything except a slow roll.

The light is seven discs stored twice, as 17-vertex fans of radius 8 and of radius 28 to 76, dark red at the centre and black at the rim, additive. Their rotation vectors advance 0.2 to 2.4 radians per frame, far too fast to read as rotation, so each disc takes an unrelated orientation every frame. With a feedback blend of 0.875 previous to 0.125 current, stronger than the tower scene's 0.625, the result is a smeared, flickering glow, with five additive flare sprites on the same point. The smoke is 128 billboards of one fog texture scattered across 805 units of depth, drifting towards the camera and recycled to the far plane. The prisms reuse the ten-pass glass renderer at half-size 1.2 with a shading callback that divides the green and blue of the reflection passes by three, which tints them red. The scene never uses VU1.

A black overlay fades out linearly with depth so the picture is clear when the camera arrives. The text is a 512 × 128 four-bit texture chosen by language (twelve variants), drawn additively, fading in one step per frame to 112. The ambience is a 5.5-minute loop. When the disc state settles, the scene stops the loop with the 1.37-second fade, fades the text out and black in over 128 frames, and returns.

## The hand-over

When the tower scene ends, the opening maps the latched disc state to what happens next: a PlayStation 2 CD or DVD becomes a launch request, a PlayStation disc another, a DVD-Video a third, an audio CD goes to the CD player, illegal media to the warning, and anything else, including no disc, to the clock and menu. If the NVRAM says the console has never been set up, the clock module runs first with its setup wizard.

For a PlayStation 2 disc, the launch routine disables the disc thread, verifies the disc and obtains its ID: key data is read from the disc twice (the SDK name is inferred), cross-checked, and decoded into the 11-character title ID. It then reads the first 1023 bytes of `cdrom0:\SYSTEM.CNF;1`, finds the `BOOT2` line, and checks that the file name after the last colon or backslash matches the first ten characters of the disc ID. Any failure sends the console to the browser. It shuts subsystems down, updates and saves the play history, and calls `LoadExecPS2("rom0:PS2LOGO", 1, {boot path})`. A PlayStation disc instead takes its ID from the `BOOT` line and goes to `rom0:PS1DRV`.

`LoadExecPS2` is the kernel routine met at power-on: terminate threads, reset hardware, re-copy EELOAD, start it with the program name; EELOAD resets the IOP for the third time, with the list inside EELOADCNF, and loads the ELF. For a game this happens twice: once for PS2LOGO and once, from inside PS2LOGO, for the game.

PS2LOGO is a self-contained, single-threaded program of about 200 KB. It reads the region from ROMVER (not from the disc), loads OSDSND and uploads a bank with one 0.45-second sample, initialises the GS, and then does the least-known thing in the PS2 boot: it reads the logo from the disc.

The lettering is not in the BIOS. PS2LOGO enables the drive's descrambler with a three-byte command (enable XOR, enable rotate, shift 5), reads sectors 0 to 11 of the disc, 24,576 bytes, and disables it. Every licensed disc carries this image in its first twelve sectors. Because the drive does the descrambling, the ROM code does not show the rule; it was taken from emulator sources and confirmed with the checksums: each raw byte is XORed with the first byte of sector 0 and rotated left by three bits. The checksum is the sum of the image's 6144 little-endian 32-bit words, which must equal 0x62DB1E66 on a Japanese or Asian console and 0x78134705 on a European one. Only J/H and E consoles check; American and Chinese consoles skip it. The two masters are regional, not per disc: of the discs checked, the European pressing of a title gives the E sum and the American pressing of the same title gives the J sum, so Japan and America share one logo image and Europe has its own. A failed checksum skips the animation and exits, which the notes infer lands in OSDSYS's error path.

The NTSC image is 384 × 64 greyscale, one byte per pixel. On PAL the same bytes are re-read as 71 rows of 344 and placed in a zero-filled 384 × 77 buffer at row 3. Either way they are drawn untinted in white, so nothing in PS2LOGO depends on the disc's type or region; a disc that shows a different logo carries different first sectors.

The animation runs at field rate on 640 × 512 buffers, and nothing clears the frame after the initial clear: it is a feedback surface. A field counter *t* starts at 17 on NTSC and 14 on PAL, skipping the first part of the authored timeline. Each field draws the logo quad (384 × 64 pixels, centred), then blurs its neighbourhood with *n* bilinear down-and-up resamples, *n* falling from 116 at *t* = 17 to 0 at *t* = 33 (roughly a 9-pixel Gaussian at the start). Over it, four vector objects in additive blending: a lavender outline of the lettering, 14 closed Bézier outlines of 721 points, unfolding from a point at the centre into the full lettering by *t* = 29; and three blue "ghost" objects, groups of letters starting enlarged three to four times and shrinking onto the lettering by *t* = 20 to 29. Each ghost is drawn as five copies at staggered times (up to 12 fields apart) with ribbons between consecutive copies at brightnesses 0, 0.3, 1.0, 0.3 and 0, brightest mid-trail: a comet.

Then the feedback: the previous field is drawn over the current one inset 2 pixels per side, at alpha 0.875 until *t* = 25, falling to 0 at *t* = 41, so the fresh logo contributes only 12.5 percent per field and the trails decay into a glow. The loop runs *t* = 17 to 42 on NTSC (26 fields, 0.43 s) and 14 to 35 on PAL (22 fields, 0.44 s). The chime is five sound effects fired at once from the one sample (fundamental about 460 Hz): copies at 0.754 and 0.744 of base pitch panned hard left and right, one at 0.561 in the centre with a slower attack, one at base pitch, and one at 0.749 with reverb.

The last frame is then held for 120 fields, 2.0 seconds on NTSC and 2.4 on PAL, while the chime rings out. The bank is freed, the driver shut down, and `LoadExecPS2` is called with the boot path OSDSYS passed in. The kernel resets, EELOAD resets the IOP, loads the game's ELF and jumps to it. The logo stays until the game resets the GS. The black period before the animation was not timed. One more unchecked detail: on NTSC, PS2LOGO's display window places the picture about 32 frame lines above the centre of the normally visible area, read from the code and not confirmed on a television.

## What the menus are

With no disc, the opening hands over to the clock module. It was surveyed, not re-created. The clock screen is a dark, time-tinted background with a 3D clock of twelve hexagonal crystal hour markers on a circle, the current hour highlighted, and a feedback-blur post pass like the opening's. The menu offers Browser and System Configuration (Clock Adjustment, Screen Size, Digital Out, Component Video Out, Language, and Remote Control when a flag is set); triangle opens Version Information, listing the registered modules. A first-time wizard runs when the NVRAM bit says the console was never configured. The menu watches the disc state every frame; a newly inserted bootable disc closes the menus and launches.

The browser shows the disc and up to eight memory-card positions. Entering a card shows one animated 3D icon per save, from the save's `icon.sys` and icon file in Sony's icon format: a vertex list with up to eight morph shapes, an animation header, and a 128 × 128 16-bit texture. Save titles are Shift-JIS, which is why every region's ROM ships the 738 KB kanji font. One hidden combination: holding Left, Square, L1, L2, R1 and R2 for 120 frames, releasing, then pressing Start resets Screen Size to 4:3, the documented way out of an unviewable setting.

## What the devkit ROM turned out to be

A survey of the DTL-H30101 development kit's BIOS (ROM 1.50 A, type D, built 28 December 2000) expected developer features and found almost none. The unit is a TEST kit with 32 MB of RAM, not the 128 MB TOOL, and its ROM is the ordinary 1.50 set: of 90 modules shared with retail 1.60 A, 69 are byte-identical, including every IOP kernel module, the boot lists, PS1DRV, OSDSND and all five asset archives. The remaining differences line up with 1.50-to-1.60 changes; the kernel's syscall table has the same 101 handlers in the same slots.

Two things are devkit-specific. The security manager is the DEX variant of SECRMAN. And the D in ROMVER is read by OSDSYS and passed, with version and region, to the drive-controller certification call at boot; retail sends C. That is the ROM's only statement of "I am a development kit"; what a devkit can boot is decided by the drive controller's firmware. There is no host file-system boot, no developer overlay, no different opening text. The kernel's boot log is written to the EE's serial port on every console, retail included; a devkit merely has the port on a connector.

## Verified, inferred, and where to look

Read from code and data, checkable against the notes' addresses: the ROMDIR layout and the LZ format; the EE call chain from reset to the opening thread; both IOP module lists; the history file's layout and rules; the slot, fill and size tables and the placement arithmetic; the camera constants and stage logic; every render stage's blend modes, constants and order; the sound driver's command set, the bank and sequence formats, the eight notes and the three cues; the disc-state codes and the launch path; PS2LOGO's sector read, checksum constants, keyframes and schedules.

Inferred, estimated or unchecked: every duration in the black period; the sequencer's exact rate and so the chime's speed-up; envelope times in seconds and the reverb's contribution; SDK names of the drive, card and SIF calls; the alpha-mask reading of the glass cubes; the orientation of the tower grid; whether tower caps overflow 8-bit colour on hardware; the NTSC placement of the logo window. A single capture of a real boot, with timestamps for the two IOP ready bits and the first visible frame, would settle most of the first group.

The tool that replays all of this from a BIOS dump, a PCSX2 memory card and an optional disc image, with every layer switchable and a free camera for the tower field, is at https://github.com/NamasteJasutin/PS2BootInspectionTool. It ships no Sony code or data; everything is read from the user's own files at run time. The `notes/` directory there holds the full write-ups this article condenses, with addresses, tables and the open questions as they stand. The readers are also available as a Rust crate, [ps2kit](https://crates.io/crates/ps2kit), and the Ghidra set-up used for the decompilation as [ps2-bios-ghidra](https://github.com/NamasteJasutin/ps2-bios-ghidra).
